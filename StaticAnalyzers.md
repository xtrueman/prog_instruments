# CI для Python: Ruff, Pyright, uv, Makefile и pre-commit

Этот гайд продолжает лекцию о статическом анализе и собирает инструменты в один рабочий процесс. На небольшом Python-проекте мы настроим окружение, проверку кода, автоисправления, форматирование, проверку типов, Git-хуки и CI. Одни и те же правила будут работать в редакторе, при ручном запуске, перед коммитом и на сервере.

Материал рассчитан на знакомство с Python, терминалом и базовыми командами Git. В примерах используется Python 3.12. Номера установленных версий и длительность команд зависят от содержимого `uv.lock` и компьютера; сокращённый вывод отдельно помечен.

## 1. Что мы хотим автоматизировать

Представим обычный pull request: разработчик добавил функцию, забыл удалить импорт, отформатировал код по-своему и передал строку туда, где ожидается число. На обсуждение стиля уходит время ревьюера, а ошибка типов обнаруживается только после запуска программы.

Часть такой работы можно выполнять автоматически. Для каждой задачи нужен понятный ответ: что проверяем, какой командой, когда и в каком окружении.

| Задача | Инструмент | Пример команды |
| --- | --- | --- |
| Найти нарушения и подозрительный код | Ruff как линтер | `uv run --locked ruff check .` |
| Исправить поддерживаемые нарушения | Ruff как автоисправлятор | `uv run --locked ruff check --fix .` |
| Привести код к единому виду | Ruff как форматтер | `uv run --locked ruff format .` |
| Проверить типы | Pyright | `uv run --locked pyright` |
| Подготовить Python и зависимости | uv | `uv sync --locked --dev` |
| Дать проверкам короткие имена | make | `make check` |
| Запустить проверки на события Git | pre-commit | `git commit`, `git push` |
| Проверить изменения на сервере | CI, например GitHub Actions | `make ci` внутри workflow |

**CI — continuous integration, непрерывная интеграция:** изменения регулярно объединяют с общей кодовой базой и автоматически проверяют. В этой лекции CI запускает линтер, проверку форматирования, тайпчекер и тесты. Сборку пакета, публикацию и развёртывание можно добавить позднее; само наличие линтера ещё не означает, что весь процесс CI настроен.

### Статический анализ, форматирование и тесты

Статический анализ исследует исходный код без его обычного выполнения. Он помогает находить неопределённые имена, неиспользуемые импорты, подозрительные конструкции, ошибки типов, некоторые проблемы безопасности и отклонения от правил проекта.

Форматтер приводит пробелы, кавычки и переносы к согласованному виду. Тест запускает код на выбранных данных и проверяет результат. Эти инструменты закрывают разные классы проблем: корректно оформленная и типизированная функция всё ещё может неправильно считать скидку.

### Какие ещё анализаторы существуют

Из прежней лекции полезно сохранить карту инструментов, но подробно разбирать всю экосистему для настройки одного проекта не требуется.

| Группа | Инструменты и назначение |
| --- | --- |
| Базовые проверки | **pycodestyle** — PEP 8; **Pyflakes** — неопределённые имена и неиспользуемые импорты; **pydocstyle** — оформление docstring |
| Составные линтеры | **Flake8** — pycodestyle, Pyflakes и плагины; **Pylint** — широкий набор проверок и метрик |
| Специализированный анализ | **Vulture** — поиск неиспользуемого кода; **Bandit** — типовые проблемы безопасности; **Semgrep** — структурные правила для разных языков |
| Объединение проверок | **Prospector**, **Pylama** — запуск нескольких анализаторов через общий интерфейс |
| Метрики и IDE | **Radon** — метрики сложности; **Wily** — их изменение во времени; **SonarLint** — анализ в IDE |
| Проверка типов | **mypy**, **Pyright**, **basedpyright**, **Pyre**, **pytype**; также **ty** и **Pyrefly** — тайпчекеры и language servers для Python |

Flake8 важен для понимания происхождения многих правил Ruff и встречается в существующих проектах. Ruff объединяет значительную часть таких проверок, сортировку импортов и автоисправления. При этом Ruff не является полной заменой каждому инструменту из таблицы: специализированный анализ безопасности или метрик может требоваться отдельно.

## 2. Сквозной пример: маленький проект с понятными проверками

В примерах одна функция считает стоимость нескольких одинаковых товаров. Отрицательное количество считается ошибкой. Такой проект достаточно мал, чтобы видеть весь путь: исходный код → диагностика → исправление → успешная проверка.

Итоговая структура:

```text
python-ci-demo/
├── main.py
├── pricing.py
├── tests/
│   └── test_pricing.py
├── pyproject.toml
├── uv.lock
├── .python-version
├── .gitignore
├── Makefile
├── .pre-commit-config.yaml
└── .github/
    └── workflows/
        └── ci.yml
```

Содержимое `pricing.py`:

```python
def total(price: float, quantity: int) -> float:
    if quantity < 0:
        raise ValueError("quantity must be >= 0")
    return price * quantity
```

Содержимое `main.py`:

```python
import pricing

print(pricing.total(100.0, 3))
```

Содержимое `tests/test_pricing.py`:

```python
import pytest

import pricing


def test_total() -> None:
    assert pricing.total(100.0, 3) == 300.0


def test_zero_quantity() -> None:
    assert pricing.total(100.0, 0) == 0.0


def test_negative_quantity() -> None:
    with pytest.raises(ValueError, match="quantity must be >= 0"):
        pricing.total(100.0, -1)
```

Это учебная арифметика, выбранная ради компактного примера. Проверки бизнес-правил и модель представления денежных значений в реальном приложении проектируют отдельно.

## 3. uv: Python, окружение и зависимости

### Какую проблему решает uv

До запуска линтера нужно ответить на несколько вопросов: какой Python используется, куда установлены зависимости и совпадают ли они с зависимостями коллеги и CI. uv управляет этими составляющими через один интерфейс.

Основные возможности uv:

- установить и выбрать версию Python;
- создать проект и виртуальное окружение `.venv`;
- добавить обычные зависимости и инструменты разработки;
- разрешить зависимости и сохранить результат в `uv.lock`;
- восстановить окружение по lock-файлу;
- запустить программу или утилиту в окружении проекта;
- временно запустить отдельный инструмент через `uvx`;
- работать с привычным форматом `requirements.txt` через команды `uv pip`.

uv и Ruff разрабатывает Astral; оба инструмента написаны на Rust. В нашем процессе скорость установки особенно полезна в новых окружениях и CI, но главный практический результат — воспроизводимый способ подготовить проект.

### Установка и начало работы

uv можно установить официальным самостоятельным установщиком, через пакетный менеджер операционной системы или как Python-пакет. Один из вариантов при уже установленном Python:

```console
$ python -m pip install uv
$ uv --version
```

После установки команда `uv` должна быть доступна в `PATH`, в том числе терминалу, из которого будет запускаться Git.

Создаём отдельный учебный проект:

```console
$ mkdir python-ci-demo
$ cd python-ci-demo
$ git init
$ uv init --bare --python 3.12
$ uv python pin 3.12
$ uv add --dev --raw ruff pyright pre-commit pytest
```

`--bare` создаёт минимальное описание проекта без лишних стартовых файлов. `uv python pin 3.12` записывает выбранную версию в `.python-version`. При необходимости Python можно заранее установить командой `uv python install 3.12`.

`--dev` помещает инструменты в группу зависимостей разработки. `--raw` сохраняет переданные имена зависимостей без добавления ограничений версий в `pyproject.toml`. Конкретные совместимые версии фиксируются в `uv.lock`; отсутствие номеров в списке зависимостей не означает установку случайных новых версий при каждом запуске.

После создания исходных файлов и настроек из этого гайда выполняем `uv lock`: это согласует lock-файл с итоговым `pyproject.toml`.

### Какие файлы за что отвечают

| Файл или каталог | Содержимое | Хранить в Git |
| --- | --- | --- |
| `pyproject.toml` | Метаданные, список зависимостей, настройки инструментов | Да |
| `uv.lock` | Разрешённые версии прямых и транзитивных зависимостей | Да |
| `.python-version` | Версия Python для локального запуска через uv | Да |
| `.venv/` | Установленное окружение конкретной машины | Нет |
| Кэши инструментов | Вспомогательные данные запусков | Нет |

Начало `pyproject.toml`:

```toml
[project]
name = "python-ci-demo"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

[dependency-groups]
dev = ["ruff", "pyright", "pre-commit", "pytest"]
```

`requires-python` описывает допустимые версии Python для проекта. `.python-version` выбирает конкретную ветку интерпретатора для рабочего окружения. Это связанные, но разные настройки; в учебном примере локально и в CI используется 3.12.

Минимальный `.gitignore`:

```gitignore
.venv/
__pycache__/
.pytest_cache/
.ruff_cache/
.pyright/
build/
dist/
```

### Самые частые команды

| Сценарий | Команда |
| --- | --- |
| Добавить библиотеку приложения | `uv add --raw httpx` |
| Удалить библиотеку | `uv remove httpx` |
| Добавить инструмент разработки | `uv add --dev --raw ruff` |
| Подготовить окружение из актуального lock-файла | `uv sync --locked --dev` |
| Запустить приложение | `uv run --locked python main.py` |
| Запустить проверку в окружении проекта | `uv run --locked ruff check .` |
| Посмотреть дерево зависимостей | `uv tree` |
| Обновить Ruff в lock-файле | `uv lock --upgrade-package ruff` |
| Обновить все допустимые зависимости | `uv lock --upgrade` |
| Разово попробовать отдельную CLI-утилиту | `uvx ruff --version` |

`uv run` запускает команду в окружении проекта и при необходимости синхронизирует его. Ручная активация `.venv` для этого не нужна. `uvx` создаёт отдельное окружение инструмента и не привязывает его к `uv.lock` проекта; поэтому в обязательных проверках далее используется `uv run --locked`.

### `--locked` и `--frozen`: существенная разница

По умолчанию uv может актуализировать lock-файл при изменении зависимостей. При обычной разработке это удобно, а в CI нежелательно: сервер должен проверить присланный набор зависимостей.

```console
$ uv sync --locked --dev
$ uv run --locked python main.py
300.0
```

`--locked` требует существующий и актуальный lock-файл. Если метаданные проекта требуют его изменения, команда завершится ошибкой. `--frozen` использует имеющийся lock-файл без проверки, соответствует ли он текущему `pyproject.toml`. Поэтому здесь выбираем `--locked`.

После намеренного изменения зависимостей:

```console
$ uv lock
$ uv sync --locked --dev
$ git diff -- pyproject.toml uv.lock
```

Затем запускаем проверки и сохраняем оба файла в одном согласованном изменении. Lock-файл редактирует uv; вручную подбирать записи внутри него не требуется.

`uv.lock` фиксирует Python-зависимости, но не всю операционную систему, системные библиотеки или внешние сервисы. Для более строгой воспроизводимости отдельно фиксируют образ среды, патч-версию Python и сам uv.

## 4. Ruff в трёх ролях

### Почему один инструмент заменяет несколько команд

Ruff поддерживает многие правила Flake8 и его плагинов, проверки Pyflakes, сортировку импортов, модернизацию синтаксиса и форматирование. Быстрый запуск позволяет использовать его в обычном цикле редактирования. Ruff работает с `.py`, `.pyi` и поддерживает Jupyter Notebook.

Внутри Ruff есть разные операции, и их нужно различать:

| Роль | Команда | Меняет файлы |
| --- | --- | --- |
| Линтер: найти нарушения | `ruff check .` | Нет |
| Автоисправлятор: применить доступные исправления | `ruff check --fix .` | Да |
| Форматтер: переписать оформление | `ruff format .` | Да |
| Проверка соответствия форматтеру | `ruff format --check .` | Нет |

Во всех практических запусках добавляем префикс `uv run --locked`, чтобы использовать Ruff из окружения проекта.

### Роль 1: линтер

Добавим в `main.py` неиспользуемый импорт:

```python
import os

import pricing

print(pricing.total(100.0, 3))
```

Проверяем только это правило, чтобы увидеть одну понятную диагностику:

```console
$ uv run --locked ruff check main.py --select F401 --output-format concise
main.py:1:8: F401 [*] `os` imported but unused
Found 1 error.
[*] 1 fixable with the --fix option.
```

Как читать сообщение: `main.py` — файл, `1:8` — строка и столбец, `F401` — правило, остальное — описание нарушения. Звёздочка сообщает о доступном автоисправлении. Точная форма сообщения может меняться с версией Ruff, а код правила позволяет найти документацию.

```console
$ uv run --locked ruff rule F401
```

Обычный `ruff check .` использует весь настроенный набор правил и возвращает ненулевой код завершения, когда остаются нарушения. Make и CI используют этот код, чтобы остановить проверку.

### Роль 2: автоисправлятор

Удаление неиспользуемого импорта — пример изменения, которое Ruff может выполнить сам:

```console
$ uv run --locked ruff check main.py --select F401 --fix
Found 1 error (1 fixed, 0 remaining).
$ git diff -- main.py
```

После исправления остаётся:

```python
import pricing

print(pricing.total(100.0, 3))
```

Чтобы заранее посмотреть предлагаемый diff, используем `ruff check --diff .`. Обычный `--fix` применяет исправления, помеченные Ruff как безопасные. Не все нарушения исправляются автоматически, и слово «безопасные» не отменяет просмотра diff и запуска тестов.

У Ruff есть отдельный режим потенциально небезопасных изменений:

```console
$ uv run --locked ruff check --fix --unsafe-fixes .
```

Такое исправление может менять поведение. Например, замена `list(values)[0]` на `next(iter(values))` меняет тип исключения для пустого набора. Этот режим применяют осознанно при отдельной правке, а не включают в обязательные автоматические проверки.

### Роль 3: автоформаттер

Возьмём тот же запуск функции с неудобным оформлением:

```python
import pricing

print( pricing.total(100.0,3) )
```

```console
$ uv run --locked ruff format main.py
1 file reformatted
```

После форматирования:

```python
import pricing

print(pricing.total(100.0, 3))
```

Форматтер отвечает за внешний вид кода. Удалять неиспользуемые импорты и сортировать импортируемые модули нужно через линтер и его исправления. Практический порядок:

```console
$ uv run --locked ruff check --fix .
$ uv run --locked ruff format .
```

В хуках и CI будет проверочная версия, которая сохраняет файлы неизменными:

```console
$ uv run --locked ruff check .
All checks passed!
$ uv run --locked ruff format --check .
3 files already formatted
```

### Набор правил: начать с понятного

У правил есть коды и семейства. Исторические префиксы удобно читать при переносе настроек Flake8.

| Префикс | Происхождение и примеры задач |
| --- | --- |
| `E`, `W` | pycodestyle: отдельные нарушения стиля |
| `F` | Pyflakes: неиспользуемые импорты, неопределённые имена |
| `I` | isort: сортировка импортов |
| `B` | flake8-bugbear: конструкции, часто приводящие к ошибкам |
| `UP` | pyupgrade: современный синтаксис Python |
| `SIM` | flake8-simplify: упрощение конструкций |
| `RUF` | Собственные правила Ruff |
| `PL` | Поддерживаемые Ruff правила семейства Pylint |
| `S` | flake8-bandit: отдельные проверки безопасности |
| `D` | pydocstyle: оформление docstring |

Для начала выбираем стабильный небольшой набор. `ALL` включает множество разнородных правил и может добавить новые требования после обновления; понимать отдельные семейства полезнее, чем исправлять всё подряд.

### Настройки Ruff в `pyproject.toml`

Добавляем к метаданным проекта:

```toml
[tool.ruff]
target-version = "py312"
line-length = 100
extend-exclude = ["generated", "build"]

[tool.ruff.lint]
select = ["E4", "E7", "E9", "F", "I", "B", "UP", "SIM"]
extend-select = ["RUF100"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
docstring-code-format = true
```

`target-version` разрешает Ruff предлагать синтаксис, доступный в Python 3.12. Это настройка анализа, а не установка интерпретатора. `line-length` задаёт желаемую длину строки; форматтер не обязан переносить абсолютно каждую длинную строку. `extend-exclude` добавляет каталоги к встроенным исключениям; `exclude` заменил бы исходный список целиком.

`select` описывает основной набор правил. Здесь включены отдельные группы `E4`, `E7`, `E9`, а не всё семейство `E`: оформление в основном поручено форматтеру. `RUF100` помогает находить ненужные подавления `noqa`. `docstring-code-format` разрешает форматировать поддерживаемые фрагменты кода внутри docstring.

Настройки Ruff также можно хранить в `ruff.toml` или `.ruff.toml`, но там секции называются `[lint]` и `[format]`, без префикса `tool.ruff`. В учебном проекте сохраняем единственный источник правил в `pyproject.toml`.

Проверить применившиеся настройки конкретного файла:

```console
$ uv run --locked ruff check main.py --show-settings
```

В большом репозитории конфигурации могут быть вложенными. При неожиданном поведении проверяем, какой файл настроек выбран: конфигурации из соседних каталогов не следует считать автоматически объединёнными. Для явного наследования у Ruff есть `extend`.

### Сортировка импортов и точечные исключения

Семейство `I` включено в нашем конфиге, поэтому обычный `ruff check --fix .` уже сортирует импорты. При желании выполнить только эту операцию:

```console
$ uv run --locked ruff check --select I --fix .
```

Для проекта со структурой `src/` можно добавить `src = ["src"]` в `[tool.ruff]`, чтобы помочь определять собственные пакеты. В небольшом проекте с модулями в корне это не требуется.

Если включены дополнительные проверки безопасности, тесты обычно используют `assert` осознанно:

```toml
[tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S101"]
```

Это дополнительный пример, а не обязательная часть нашего минимального конфига: `S101` имеет смысл исключать, только если оно включено. Подавление на отдельной строке ещё уже:

```python
from package import public_api  # noqa: F401
```

Так можно обозначить намеренный публичный реэкспорт. Сначала стоит проверить, можно ли явно описать API через `__all__` или подходящий импорт. Подавление без кода правила скрывает слишком много; глобальное `ignore` выключает проверку во всём проекте.

### Редактор и миграция

Для быстрой обратной связи подключаем официальный Ruff-плагин редактора и выбираем Ruff как форматтер. Настройки правил читаются из репозитория. Автоформатирование при сохранении удобно, но не заменяет проверку в CI: код можно изменить другим редактором или скриптом.

Переход со старой связки полезно разделить на несколько изменений:

1. Перенести нужные правила Flake8 и плагинов в Ruff, сравнить результаты без автоисправлений.
2. Отдельно применить безопасные исправления и проверить diff.
3. Отдельно согласовать форматтер и применить форматирование.
4. Удалить дублирующиеся запуски Flake8, isort и Black там, где Ruff действительно их заменил.
5. Добавлять новые строгие правила постепенно.

Ruff Formatter близок к стилю Black, но не обещает побайтово одинаковый результат. Одновременно запускать два форматтера для одних и тех же файлов обычно не требуется.

## 5. Pyright: ошибки, которые не сводятся к стилю

### Что проверяет тайпчекер

Аннотации типов описывают договор между частями программы. Pyright проверяет, что аргументы, возвращаемые значения и операции соответствуют этому договору. Он анализирует связи между модулями, выводит типы и уточняет их после условий.

Например, у функции `pricing.total` второй аргумент объявлен как `int`. Изменим `main.py`:

```python
import pricing

print(pricing.total(100.0, "3"))
```

Ruff может не найти здесь нарушения своих правил: строка оформлена правильно и имена существуют. Pyright обнаружит несоответствие. Сокращённый вывод:

```console
$ uv run --locked pyright
main.py:3:28 - error: Argument of type "Literal['3']" cannot be assigned to parameter "quantity" of type "int" in function "total"
  "Literal['3']" is not assignable to "int" (reportArgumentType)
1 error, 0 warnings, 0 informations
```

Исправление — передать `3` или явно преобразовать полученную извне строку в число в подходящем месте. После исправления:

```console
$ uv run --locked pyright
0 errors, 0 warnings, 0 informations
```

Pyright не проверяет значения, полученные по сети, во время работы приложения. Валидация входных данных и обработка ошибок остаются частью кода. `Any` также ослабляет статическую проверку: им не стоит заменять непонятный тип только ради зелёного отчёта.

### Почему в лекции выбран Pyright

Pyright быстро выполняет полный и инкрементальный анализ, поддерживает современную типизацию Python и подходит для постоянной работы в редакторе и CI. Он понимает объединения типов, generics, протоколы, overloads, type stubs и сужение типов. Его движок используется в Pylance, но CLI Pyright и расширение Pylance — разные продукты с разными циклами обновления.

Исходный Pyright Microsoft распространяется как Node.js-пакет. Пакет `pyright` из PyPI — поддерживаемая сообществом Python-обёртка, которую удобно установить через uv; она организует запуск Pyright и необходимого Node.js. Для первого запуска может понадобиться сеть. Это следует учитывать в полностью закрытом CI-окружении.

### Конфигурация Pyright

Добавляем в тот же `pyproject.toml`:

```toml
[tool.pyright]
include = ["main.py", "pricing.py", "tests"]
exclude = ["**/__pycache__", "build", "generated"]
pythonVersion = "3.12"
typeCheckingMode = "strict"
venvPath = "."
venv = ".venv"
```

`include` задаёт начальную область анализа. `exclude` исключает пути из обхода, но импортированный из проверяемого кода модуль всё равно может участвовать в анализе. `pythonVersion` задаёт целевую версию языка, а `venvPath` и `venv` помогают CLI найти зависимости в `.venv`.

`typeCheckingMode` выбирает набор проверок: `off`, `basic`, `standard` или `strict`. В новом маленьком проекте удобно начать со `strict`. В крупной существующей базе разумно начать со `standard` и повышать строгость постепенно. `pythonPlatform`, `extraPaths` и отдельные `report*`-настройки пригодятся при более сложной структуре и окружении.

Альтернатива TOML — `pyrightconfig.json`. Если оба файла присутствуют, JSON имеет приоритет: случайно оставленный старый конфиг может объяснять неожиданный результат. В VS Code нужно также выбрать правильный интерпретатор Python для редактора.

### Сужение типа: от `str | None` к `str`

Следующий пример самостоятельный и не требует добавления в учебный проект:

```python
def length(value: str | None) -> int:
    if value is None:
        return 0
    return len(value)
```

После раннего `return` значение `None` уже невозможно. Pyright понимает, что в последней строке `value` имеет тип `str`. Аналогичные выводы возникают после `isinstance`, веток `match`, проверок литералов и других поддерживаемых условий.

Для исследования вывода типов можно временно добавить `reveal_type`:

```python
from typing import reveal_type


def length(value: str | None) -> int:
    if value is None:
        return 0
    reveal_type(value)
    return len(value)
```

Pyright покажет `Type of "value" is "str"`. Это информационное сообщение, а не type error; счётчик `informations` станет ненулевым. После исследования такой вызов обычно удаляют из рабочего кода.

### Постепенное внедрение и basedpyright

Pyright позволяет включать строгую проверку для отдельных путей:

```toml
[tool.pyright]
include = ["src", "tests"]
typeCheckingMode = "standard"
strict = ["src/new_api"]
```

Сначала исправляем неверные импорты и очевидные несовместимости, затем аннотируем границы модулей и расширяем строгую область. Прежде чем выключать `report*`-диагностику, стоит разобраться с конкретным примером и качеством типов сторонней библиотеки.

**basedpyright** — форк Pyright с более строгими настройками по умолчанию, дополнительными диагностическими правилами и baseline. Baseline позволяет зафиксировать существующие срабатывания и отслеживать новые, постепенно сокращая накопленный долг. Форк также развивает возможности language server и поставку через Python-пакет.

Если команда выбирает basedpyright, его можно использовать вместо Pyright:

```toml
[tool.basedpyright]
include = ["main.py", "pricing.py", "tests"]
typeCheckingMode = "recommended"
failOnWarnings = true
```

Тогда меняются зависимость, раздел конфигурации и команда в Makefile на `basedpyright`. Запускать оба тайпчекера одновременно для этого учебного процесса не нужно. Выбор Pyright здесь — осознанный вариант связки; «лучший тайпчекер» зависит от требуемых проверок, экосистемы и принятого уровня строгости.

## 6. make и Makefile: от компиляции к командам проекта

### Откуда появился make

make создал Stuart Feldman в Bell Labs в 1970-х годах. Технический отчёт относится к 1977 году, статья «Make: A Program for Maintaining Computer Programs» опубликована в 1979 году.

Задача была вполне практической: большая программа состоит из многих исходных файлов. После изменения одного из них нужно перекомпилировать нужные части и заново собрать программу. Повторять всю сборку долго, а вручную помнить каждую зависимость ненадёжно.

make предлагает описать файлы, их зависимости и команды построения. Инструмент сравнивает время изменения файлов и решает, какие результаты устарели. Эта идея полезна и за пределами C/C++: для генерации документации, преобразования данных и обработки медиафайлов.

`make` — утилита, которую запускают. `Makefile` — текстовый файл с правилами. GNU Make — одна из реализаций make. В примерах далее используется совместимый с GNU Make синтаксис; базовые правила переносимы, а доступность утилиты зависит от среды. На Windows для учебного проекта удобно использовать WSL, где доступны make и обычная Unix-оболочка.

### Классическая сборка: компиляция и линковка

Пусть программа состоит из `main.c`, `math.c` и общего заголовка `math.h`. Сначала компилятор превращает каждый `.c` в объектный `.o`, затем линкер объединяет объектные файлы в исполняемый файл `calculator`.

```text
main.c + math.h ──компиляция──> main.o ──┐
                                       ├──линковка──> calculator
math.c + math.h ──компиляция──> math.o ──┘
```

Без make команды выглядят так:

```console
$ cc -Wall -Wextra -O2 -c main.c -o main.o
$ cc -Wall -Wextra -O2 -c math.c -o math.o
$ cc main.o math.o -o calculator
```

`-c` означает компиляцию без линковки, `-o` задаёт выходной файл. Если изменился только `math.c`, достаточно повторить вторую и третью команды. Если изменился общий заголовок, нужно заново скомпилировать оба исходника.

### Полный маленький пример на C

Этот пример находится в отдельном каталоге от Python-проекта. `math.h`:

```c
#ifndef MATH_H
#define MATH_H

int add(int left, int right);

#endif
```

`math.c`:

```c
#include "math.h"

int add(int left, int right) {
    return left + right;
}
```

`main.c`:

```c
#include <stdio.h>
#include "math.h"

int main(void) {
    printf("%d\n", add(2, 3));
    return 0;
}
```

Минимальный `Makefile` повторяет граф:

```makefile
calculator: main.o math.o
	cc main.o math.o -o calculator

main.o: main.c math.h
	cc -Wall -Wextra -O2 -c main.c -o main.o

math.o: math.c math.h
	cc -Wall -Wextra -O2 -c math.c -o math.o
```

```console
$ make calculator
cc -Wall -Wextra -O2 -c main.c -o main.o
cc -Wall -Wextra -O2 -c math.c -o math.o
cc main.o math.o -o calculator
$ ./calculator
5
```

### Синтаксис правила и символ TAB

Общая форма:

```makefile
target: prerequisite_a prerequisite_b
	recipe command
```

`target` — имя результата, `prerequisites` — зависимости, которые нужны для его получения, `recipe` — команда построения. Перед командой в классическом синтаксисе стоит **настоящий TAB**, а не четыре или восемь пробелов. При копировании Makefile нужно сохранить табуляцию; типичная ошибка из-за её потери — `missing separator`.

У правила может быть несколько команд, а у составной цели — зависимости без собственных команд. Если не указать цель при запуске, make обычно выберет первую обычную цель файла. Для явного выбора у GNU Make есть `.DEFAULT_GOAL`.

По умолчанию make печатает рецепт перед выполнением. Префикс `@` скрывает печать самой команды, но не её вывод. Ненулевой код завершения команды останавливает соответствующую цепочку сборки: это же поведение позже понадобится для проверок кода.

### Когда make выполняет работу повторно

Файловая цель требует обновления, когда она отсутствует или одна из обычных зависимостей новее неё. Если ничего не менялось, повторный запуск не компилирует файлы заново.

```console
$ make calculator
make: 'calculator' is up to date.
$ touch math.c
$ make calculator
cc -Wall -Wextra -O2 -c math.c -o math.o
cc main.o math.o -o calculator
```

`main.o` остался актуальным. После `touch math.h` понадобятся обе компиляции и линковка: заголовок указан в зависимостях обеих объектных целей.

make сравнивает временные метки, а не смысл кода. Если рецепт забывает перечислить важный входной файл, инструмент не угадает эту зависимость. Изменение команды компиляции само по себе тоже не делает все объектные файлы устаревшими; это нужно учитывать при устройстве реальной сборки.

### Переменные, шаблонные правила и автоматические переменные

Повторяющиеся команды можно записать короче:

```makefile
CC = cc
CFLAGS = -Wall -Wextra -O2
OBJ = main.o math.o

calculator: $(OBJ)
	$(CC) $(CFLAGS) $^ -o $@

%.o: %.c math.h
	$(CC) $(CFLAGS) -c $< -o $@
```

Зависимость от `math.h` сохранена в шаблонном правиле. Без неё сокращённый вариант пропустил бы пересборку после изменения заголовка.

| Запись | Значение |
| --- | --- |
| `$(CC)` | Значение переменной `CC` |
| `$@` | Имя текущей цели |
| `$<` | Первая зависимость; в шаблонном правиле — соответствующий `.c` |
| `$^` | Все зависимости без повторений |
| `%` | Совпадающая часть имени в шаблонном правиле |

В больших C/C++-проектах список заголовков обычно генерирует сам компилятор в `.d`-файлы. Здесь зависимости перечислены вручную, чтобы механизм был виден полностью.

Операторы присваивания тоже различаются:

| Оператор | Поведение |
| --- | --- |
| `=` | Значение разворачивается при использовании |
| `:=` | Значение вычисляется при чтении строки Makefile |
| `?=` | Задать значение, только если переменная ещё не определена |
| `+=` | Дописать к значению |

Параметры командной строки обычно переопределяют обычные присваивания Makefile:

```console
$ make calculator CFLAGS="-Wall -Wextra -O0 -g"
```

Для уже собранных объектов смена `CFLAGS` сама по себе не гарантирует повторную компиляцию. Для демонстрации можно запросить принудительную сборку `make -B calculator CFLAGS="-Wall -Wextra -O0 -g"`.

### make не обязан собирать исполняемые программы

Пусть из аудиозаписи нужно получить текст, а затем краткое резюме. В отдельном проекте уже установлены Whisper, его системные зависимости и подготовлен скрипт `summarize.py`, который читает переданный текстовый файл и печатает резюме в stdout.

```makefile
interview.txt: interview.wav
	uv run --locked whisper $< --model small --output_format txt --output_dir .

summary.txt: interview.txt summarize.py
	uv run --locked python summarize.py $< > $@
```

Whisper создаёт `interview.txt` по имени входного `interview.wav`, поэтому имя файловой цели совпадает с реальным результатом команды. Вторая цель зависит и от транскрипта, и от кода обработчика: изменение `summarize.py` должно пересоздать резюме.

```console
$ make summary.txt
uv run --locked whisper interview.wav --model small --output_format txt --output_dir .
uv run --locked python summarize.py interview.txt > summary.txt
```

Здесь показаны команды make без подробного вывода моделей. В реальном сценарии учитывают также версию модели, параметры обработки и внешние входы. Если они важны для актуальности результата, их описывают как зависимости, например через отдельный файл конфигурации.

### `.PHONY`: от файлов к действиям

Для запуска линтера не нужен файл с именем `lint`. Нужна команда, которая выполняется каждый раз. Однако обычный make ориентирован на файлы: появившийся файл `lint` может убедить его, что цель уже готова.

`.PHONY` объявляет имя действием:

```makefile
.PHONY: lint test check

lint:
	uv run --locked ruff check .

test:
	uv run --locked pytest -q

check: lint test
```

`make lint` теперь запускает линтер независимо от наличия одноимённого файла. `make check` выполняет обе зависимости. Сам `check` не обязан иметь рецепт.

Файловые цели вроде `calculator` и `summary.txt` оставляем обычными, чтобы работала инкрементальная сборка. Цели `run`, `test`, `lint`, `fix`, `help` обычно объявляем `.PHONY`.

### Частые команды и окружение оболочки

Makefile может содержать команды запуска приложения, тестов, генерации данных и локальной инфраструктуры. Имена выбирает команда проекта:

```makefile
UV ?= uv
RUN := $(UV) run --locked
TEST_ARGS ?= -q

.PHONY: run test

run:
	$(RUN) python main.py

test:
	$(RUN) pytest $(TEST_ARGS)
```

```console
$ make run
uv run --locked python main.py
300.0
$ make test TEST_ARGS="-q -x"
```

Каждая строка рецепта по умолчанию исполняется в отдельной оболочке. Поэтому `cd folder` на одной строке не изменит каталог для следующей строки. Связанные действия записывают в одной строке, например `cd folder && command`, или выбирают инструмент с явным параметром каталога.

По той же причине активация `.venv` отдельной строкой рецепта не подготавливает следующую строку. `uv run` решает вопрос окружения непосредственно при запуске каждой команды.

Чтобы передать знак `$` именно оболочке, в Makefile пишут `$$`. Например, `$$HOME` станет `$HOME` для shell, а `$(UV)` обрабатывает сам make. Секреты не хранят в Makefile; их передают через окружение или настройки CI.

### Диагностика и параллельный запуск

```console
$ make -n check
$ make -j 4 check
```

`-n` показывает план команд без обычного выполнения рецептов. `-j 4` разрешает несколько независимых работ одновременно. Если зависимость должна завершиться раньше другой, это нужно выразить графом, а не только порядком имён в строке.

Проверки чтения кода обычно можно распараллелить после подготовки окружения. Автоисправления и форматирование одного набора файлов запускаем последовательно. В нашем учебном сценарии `make sync` выполняется заранее, а обычные `make check` и хуки запускаются без `-j`: это упрощает вывод и исключает одновременную первоначальную настройку общего окружения.

make полезен даже как набор коротких команд, хотя его файловая модель здесь используется лишь частично. Для сравнения существуют **just**, **Taskfile**, **tox**, **nox**, **Snakemake**, **doit**, а менеджеры проектов могут поддерживать собственные сценарии. В этой лекции выбираем make, чтобы понять и классическую сборку, и организацию команд проекта одним инструментом.

## 7. Собираем единый интерфейс Python-проекта

### Полный `pyproject.toml`

Ниже итоговый файл для сквозного примера. Отдельные конфигурационные фрагменты выше объясняли настройки; здесь они уже объединены, повторять одни и те же TOML-секции не нужно.

```toml
[project]
name = "python-ci-demo"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

[dependency-groups]
dev = ["ruff", "pyright", "pre-commit", "pytest"]

[tool.ruff]
target-version = "py312"
line-length = 100
extend-exclude = ["generated", "build"]

[tool.ruff.lint]
select = ["E4", "E7", "E9", "F", "I", "B", "UP", "SIM"]
extend-select = ["RUF100"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"
docstring-code-format = true

[tool.pyright]
include = ["main.py", "pricing.py", "tests"]
exclude = ["**/__pycache__", "build", "generated"]
pythonVersion = "3.12"
typeCheckingMode = "strict"
venvPath = "."
venv = ".venv"

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
```

Настройки pytest задают каталог тестов и путь импорта корневых модулей. Для устанавливаемого пакета со структурой `src/` схема импорта будет другой; в этом маленьком примере важно, чтобы `pricing` одинаково находился при запуске приложения, тайпчекера и тестов.

После сохранения файла:

```console
$ uv lock
$ uv sync --locked --dev
```

### Полный `Makefile`

```makefile
UV ?= uv
RUN := $(UV) run --locked
.DEFAULT_GOAL := check

.PHONY: sync hooks lint format-check fix typecheck test check hook-commit hook-push ci run

sync:
	$(UV) sync --locked --dev

hooks:
	$(RUN) pre-commit install --hook-type pre-commit --hook-type pre-push

lint:
	$(RUN) ruff check .

format-check:
	$(RUN) ruff format --check .

fix:
	$(RUN) ruff check --fix .
	$(RUN) ruff format .

typecheck:
	$(RUN) pyright

test:
	$(RUN) pytest -q

hook-commit: lint format-check

hook-push: typecheck test

check: lint format-check typecheck test

ci: check

run:
	$(RUN) python main.py
```

`make` без аргумента теперь означает `make check`. Цель `sync` подготавливает окружение, `hooks` устанавливает обработчики Git, `fix` явно изменяет исходники. Остальные проверки код не переписывают.

`fix` содержит две последовательные команды. Если после автоматических исправлений остаётся неисправленная ошибка линтера, первая команда возвращает ненулевой код и make останавливается. Нужно разобрать диагностику, исправить её вручную и повторить запуск; для отдельного форматирования доступна команда `uv run --locked ruff format .`.

| Команда | Когда использовать |
| --- | --- |
| `make sync` | После клонирования и изменения зависимостей |
| `make hooks` | Один раз в каждой локальной копии после подготовки окружения |
| `make run` | Запустить приложение |
| `make lint` | Посмотреть нарушения Ruff |
| `make fix` | Осознанно применить автоисправления и форматирование |
| `make format-check` | Проверить форматирование без изменения файлов |
| `make typecheck` | Проверить типы во всём выбранном проекте |
| `make test` | Запустить тесты |
| `make check` | Выполнить все четыре проверки |
| `make ci` | Выполнить тот же полный набор в CI |

`hook-commit` и `hook-push` — обычные составные цели. Их можно запустить руками, но Git будет вызывать их автоматически после настройки pre-commit.

## 8. pre-commit и Git-хуки

### Зачем нужны хуки

Удобная команда помогает только тому, кто не забыл её выполнить. Git-хук связывает действие с событием: проверить стиль перед созданием коммита, проверить типы и тесты перед отправкой изменений.

Git сам поддерживает хуки — исполняемые обработчики событий. Пакет и CLI **`pre-commit`** помогают описать их в конфиге, установить и одинаково запускать. Имя пакета пишется через дефис; его возможности не ограничиваются событием `pre-commit`.

| Стадия | Когда вызывается | Что запускаем |
| --- | --- | --- |
| `pre-commit` | Перед созданием коммита | Ruff lint и проверку форматирования |
| `pre-push` | Перед отправкой изменений на сервер | Pyright и тесты |
| CI | На сервере для присланного изменения | Все четыре проверки |

Быстрые проверки дают раннюю обратную связь на каждом коммите. Проверки типов и тесты перенесены на push, чтобы не замедлять создание небольших промежуточных коммитов. Для совсем маленького проекта допустимо запускать всё уже на commit; это решение команды о скорости обратной связи.

### Почему используем локальные хуки, вызывающие make

pre-commit умеет устанавливать готовые хуки из сторонних репозиториев и создавать для них отдельные окружения. Это удобно, например, для стандартных проверок YAML и окончания строк.

Здесь уже есть окружение uv и Makefile с нужными командами. Используем `repo: local`, чтобы каждый путь запуска обращался к ним. Версии Ruff, Pyright, pytest и самого pre-commit приходят из `uv.lock`, а правила — из `pyproject.toml`.

Содержимое `.pre-commit-config.yaml`:

```yaml
minimum_pre_commit_version: '4.4.0'
default_install_hook_types: [pre-commit, pre-push]

repos:
  - repo: local
    hooks:
      - id: project-style
        name: Ruff checks
        entry: make hook-commit
        language: unsupported
        pass_filenames: false
        always_run: true
        require_serial: true
        stages: [pre-commit]

      - id: project-types-tests
        name: Pyright and tests
        entry: make hook-push
        language: unsupported
        pass_filenames: false
        always_run: true
        require_serial: true
        stages: [pre-push]
```

`language: unsupported` означает, что pre-commit сам не создаёт языковое окружение для этой команды: необходимую среду предоставляет uv. Это актуальное название начиная с pre-commit 4.4.0; в старых примерах встречается `language: system`, которое стало устаревающим псевдонимом. `minimum_pre_commit_version` явно показывает требование конфигурации.

Разберём остальные поля:

- `id` — стабильный идентификатор хука, используемый при ручном запуске;
- `name` — подпись в отчёте;
- `entry` — запускаемая команда;
- `stages` — событие, для которого она предназначена;
- `pass_filenames: false` — не добавлять список изменённых файлов к команде;
- `always_run: true` — выполнять проверку даже без подходящего набора файлов;
- `require_serial: true` — выполнять этот хук одним процессом, не делить входы на параллельные запуски.

`pass_filenames: false` здесь принципиален: команда `make hook-commit main.py` восприняла бы `main.py` как ещё одну цель make. Мы хотим вызвать уже описанную команду и проверить проект целиком. `always_run` помогает не пропустить изменения конфигурации или зависимостей. `require_serial` относится к механизму pre-commit и сам по себе не запрещает внутренний `make -j`.

### Установка в локальную копию проекта

Сначала синхронизируем окружение, затем устанавливаем оба вида хуков:

```console
$ make sync
$ make hooks
uv run --locked pre-commit install --hook-type pre-commit --hook-type pre-push
pre-commit installed at .git/hooks/pre-commit
pre-commit installed at .git/hooks/pre-push
```

Установка записывает обработчики в локальный каталог Git. Сам `.pre-commit-config.yaml` хранится в репозитории, но эти обработчики не приезжают к коллеге автоматически при клонировании: в своей копии он тоже выполняет `make sync` и `make hooks`.

В учебном примере `uv` и `make` должны быть доступны среде, из которой запускается Git. Если терминал проходит проверки, а Git-клиент с графическим интерфейсом сообщает `command not found`, сравниваем их `PATH`.

### Проверка конфигурации и ручной запуск

```console
$ uv run --locked pre-commit validate-config
$ uv run --locked pre-commit run --all-files --hook-stage pre-commit
Ruff checks..............................................................Passed
$ uv run --locked pre-commit run --all-files --hook-stage pre-push
Pyright and tests.........................................................Passed
```

Длина точек в реальном отчёте может отличаться. Параметр `--hook-stage` нужен, чтобы явно проверить выбранное событие: обычный запуск не обязан выполнить хуки всех стадий.

Отдельный хук можно вызвать по идентификатору:

```console
$ uv run --locked pre-commit run project-style --all-files --hook-stage pre-commit
```

### Что происходит при ошибке

Если перед коммитом добавить неиспользуемый импорт, Git вызовет pre-commit, тот — `make hook-commit`, а make — Ruff. Ненулевой код завершения остановит коммит. Сокращённый отчёт:

```console
$ git commit -m "Add pricing calculation"
Ruff checks..............................................................Failed
- hook id: project-style
- exit code: 2
```

Под ним будет диагностика Ruff и make. Код оболочки make может отличаться от кода самого Ruff: важен факт неуспеха, который распространяется до Git.

Обычный цикл исправления:

```console
$ make fix
$ git diff
$ make check
$ git add main.py pricing.py tests/test_pricing.py
$ git commit -m "Add pricing calculation"
```

Хуки этой связки не исправляют код автоматически. Разработчик видит diff, добавляет исправленные файлы в индекс и повторяет коммит. Если использовать готовые автоисправляющие хуки, обычно также потребуется повторный `git add`; это другой допустимый сценарий, но в нашем примере проверка и изменение кода разделены явно.

### Какие файлы на самом деле проверяются

По умолчанию pre-commit ориентируется на подготовленные к коммиту файлы. При commit он временно скрывает незастейдженные изменения в отслеживаемых файлах, выполняет хуки и затем восстанавливает эти изменения.

Наши команды проверяют **весь проект**, потому что линтер получает `.`, а Pyright читает область анализа из конфига. Поэтому возможны два полезных, но важных эффекта:

1. Проверку может остановить ошибка в другом модуле, даже если именно этот модуль не менялся в коммите.
2. Инструменты могут увидеть новые неотслеживаемые файлы, доступные при обходе рабочего каталога. Такой запуск нельзя без оговорок называть идеальным снимком Git-index.

Зависимости нужно подготавливать заранее; `pyproject.toml` и `uv.lock` добавляем в коммит согласованно. Иначе после временного скрытия незастейдженной части изменений `--locked` закономерно обнаружит рассогласование.

Хук `pre-push` с нашими командами проверяет текущее рабочее дерево. Он не переключается автоматически на каждый отправляемый коммит и не проверяет каждый из них отдельно. CI получает отдельную рабочую копию ревизии события `push` или `pull_request`. Для `pull_request` стандартный checkout обычно проверяет тестовое объединение ветки pull request с целевой веткой.

### Хуки полезны, но не обязательны для всех сами по себе

Локальные хуки можно не установить или обойти средствами Git/pre-commit. Поэтому их задача — ранняя обратная связь, а обязательность задаётся серверными проверками и правилами слияния pull request.

Связь должна оставаться односторонней:

```text
Git → pre-commit → make hook-commit / hook-push → uv → инструменты
```

Не нужно вызывать `pre-commit run` из `make check`, если эти же хуки вызывают `make check`: получится рекурсивный запуск. Цель `ci` также обращается напрямую к проверкам Makefile.

## 9. CI: те же команды на сервере

### Минимальный GitHub Actions workflow

CI начинает работу в отдельной среде. Ему нужно получить код, установить uv и Python, восстановить зависимости из lock-файла и запустить `make ci`.

Содержимое `.github/workflows/ci.yml`:

```yaml
name: CI

on: [push, pull_request]

permissions:
  contents: read

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: astral-sh/setup-uv@20cfd1bf945f4377ade1205e4dbc17946fc9a30d # v10.0.1
        with:
          enable-cache: true
          python-version: '3.12'
      - run: make sync
      - run: make ci
```

Здесь версии actions закреплены полными SHA, проверенными по официальным репозиториям. Комментарии помогают узнать соответствующие релизы. Это проверяемые версии примера, а не утверждение, что они всегда самые новые; обновление actions — отдельное изменение проекта. В кратких примерах встречаются теги `@v7` и `@v10.0.1`; полная ссылка на коммит точнее фиксирует исполняемый action.

`push` проверяет отправленные изменения, `pull_request` — изменения в контексте pull request. В зависимости от сценария эти события могут дать два запуска для одного изменения; позже можно сузить триггеры. `contents: read` даёт workflow доступ на чтение кода. `enable-cache` ускоряет загрузку зависимостей, но не заменяет `uv.lock`.

`setup-uv` устанавливает uv и задаёт выбранную версию Python. Сам интерпретатор при необходимости установит uv во время синхронизации. `make sync` проверяет актуальность lock-файла и подготавливает dev-зависимости. `make ci` запускает тот же набор, который доступен локально. Устанавливать Git-хуки внутри CI для этого не нужно.

В этом минимальном workflow сам uv и образ `ubuntu-latest` не зафиксированы до неизменяемого снимка. Когда проекту нужна более строгая воспроизводимость, задают проверенную версию uv в `setup-uv`, версию образа и более точную версию Python.

### Почему CI не исправляет исходники

CI должен сообщить, соответствует ли присланный код правилам. Если он незаметно отформатирует свою временную копию и завершится успешно, исходный коммит останется неотформатированным.

Поэтому `make ci` выполняет `ruff check` и `ruff format --check`, а не `--fix` и обычный `ruff format`. Исправление делается локально, просматривается и отправляется новым изменением.

### Когда проверка действительно становится обязательной

Наличие YAML-файла запускает workflow, но само по себе не запрещает слияние. В настройках репозитория нужно назначить успешный статус job `quality` обязательной проверкой для защищённой ветки или соответствующего ruleset.

Тогда pull request с ошибкой Ruff, несовместимым типом или упавшим тестом не сможет пройти установленное правило слияния. Конкретные права обхода и политика веток остаются настройками команды.

### Когда разработчик получает обратную связь

```text
Редактирование   → Ruff / Pyright в редакторе
Ручная проверка  → make check
git commit      → pre-commit → make hook-commit → Ruff + format-check
git push        → pre-commit → make hook-push   → Pyright + tests
Pull request    → CI → make sync → make ci     → все проверки
```

`pyproject.toml` хранит правила, `uv.lock` — зависимости, Makefile — команды, `.pre-commit-config.yaml` — события локального Git, workflow — серверный запуск. Такое разделение позволяет менять правило линтера в одном месте и получать его на всех этапах.

## 10. Практика: внедрение, демонстрация и типичные сбои

### Как запустить готовый учебный проект

После создания файлов из разделов выше:

```console
$ uv lock
$ make sync
$ make fix
$ make check
$ make hooks
$ git add main.py pricing.py tests/test_pricing.py pyproject.toml uv.lock
$ git add .python-version .gitignore Makefile .pre-commit-config.yaml .github/workflows/ci.yml
$ git commit -m "Configure Python quality checks"
```

После клонирования готового проекта с закоммиченным `uv.lock` последовательность короче:

```console
$ make sync
$ make hooks
$ make check
$ make run
```

Перед публикацией изменений полезно отдельно проверить оба hook-stage через `pre-commit run`, как показано выше. Успешный локальный запуск не заменяет первый запуск workflow на сервере: он дополнительно проверит доступность окружения и установку зависимостей в CI.

### Сценарий демонстрации на лекции

1. Запустить исходный проект: приложение печатает `300.0`, все проверки проходят.
2. Добавить `import os`: `make lint` показывает `F401`.
3. Выполнить `make fix`, просмотреть diff: импорт удалён автоматически.
4. Испортить пробелы вокруг вызова: `make format-check` сообщает о необходимости форматирования.
5. Передать `"3"` вместо `3`: Ruff может пройти, `make typecheck` покажет ошибку аргумента.
6. Временно удалить проверку отрицательного количества в `pricing.total`: типы остаются корректными, но `make test` обнаруживает нарушение ожидаемого поведения.
7. Восстановить функцию, установить хуки, повторить ошибку импорта и показать остановку коммита.
8. Исправить код, выполнить `git add` и успешно повторить коммит.
9. Запустить стадию `pre-push` вручную и показать полный набор `make ci`.
10. Открыть результат workflow в pull request и найти конкретный шаг с диагностикой.

Так каждый инструмент демонстрируется на ошибке, которую действительно должен обнаруживать, а студент видит причину наличия нескольких видов проверок.

### Как внедрить связку в существующий проект

Сначала описываем зависимости через uv и добиваемся воспроизводимого запуска текущих тестов. Затем добавляем Ruff в режиме проверки с небольшим набором правил. Массовые автоисправления и форматирование делаем отдельными понятными изменениями.

Pyright сначала можно направить на активно изменяемые модули, постепенно расширяя область и строгость. После появления понятных и достаточно быстрых команд объединяем их в Makefile, подключаем хуки и добавляем обязательный CI.

Не стоит объявлять успехом ситуацию, где вся старая кодовая база скрыта глобальными `ignore`, а проверяется только пустой каталог. С другой стороны, мгновенное включение всех возможных правил может превратить внедрение в бесконечное исправление стиля. Полезный критерий — какие реальные ошибки команда стала находить раньше и насколько понятна диагностика.

### Частые проблемы и их причины

| Симптом | Что проверить |
| --- | --- |
| `missing separator` | Сохранены ли настоящие TAB перед рецептами Makefile |
| `make lint` ничего не делает | Объявлен ли `lint` в `.PHONY`, нет ли одноимённого файла |
| Команда работает в терминале, но не в Git-клиенте | Доступны ли `uv` и `make` в `PATH` этого процесса |
| uv сообщает об устаревшем lock-файле | Согласованы ли `pyproject.toml` и `uv.lock`; выполнен ли `uv lock` после намеренного изменения |
| Pyright не находит установленную библиотеку | Выполнен ли `make sync`; выбран ли нужный интерпретатор и `.venv` |
| Ruff и CI видят разные правила | Нет ли второго конфига, вложенных настроек или разных версий инструмента |
| После `make fix` коммит всё ещё отклоняется | Остались ли неисправимые автоматически ошибки; добавлены ли изменения повторным `git add` |
| pre-commit не запускается после клонирования | Выполнен ли `make hooks` в этой локальной копии |
| `pre-push` не проверяется ручной командой | Указан ли `--hook-stage pre-push` |
| Хук запускается бесконечно | Не вызывает ли Makefile pre-commit, который снова вызывает эту же цель |
| Локально всё зелёное, а CI красный | Совпадают ли ревизия, Python, lock-файл, доступность файлов и системные зависимости |

### Что должно остаться после лекции

У проекта есть одна команда подготовки окружения, одна команда полной проверки и понятная команда исправления. Разработчик получает быстрый ответ до отправки кода, а сервер повторяет проверки независимо от его локальных настроек. Команда понимает не только названия инструментов, но и цепочку вызовов, файлы конфигурации и причины возможных ошибок.
